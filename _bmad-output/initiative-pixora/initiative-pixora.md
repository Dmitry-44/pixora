# pixora

## Description

Pixora MVP — Telegram-бот для закрытого круга (автор, друзья, знакомые), который по свободному текстовому запросу генерирует одно изображение через Polza.ai и присылает его в чат. Проект личный: ценность — в отказоустойчивом бэкенде и новом для автора стеке как кейсе для портфолио, а не в функциях бота (бриф, «Кратко»). Когда инициатива завершена, бот работает в проде, переживает рестарты и сбои провайдера без потери запросов и молчаливых отказов, а архитектура задокументирована. Код пишется с нуля.

## Outcome

Автор получает работающий в проде бот и портфолио-кейс, где отказоустойчивость демонстрируется вживую: сигнал — критерии успеха брифа 1–3.

## Requirements

- R1 (brief «Что строим в MVP», «Критерии успеха» 1): пользователь из белого списка отправляет текст и получает одно изображение ответом на своё сообщение; изображение больше лимита фото Telegram приходит файлом.
- R2 (brief «Пользователи и доступ»): пользователь вне белого списка получает короткий отказ; генерация не запускается, ничего не сохраняется.
- R3 (brief «Что строим в MVP»): подтверждение «принято» приходит сразу, до готовности изображения; приём новых сообщений не ждёт идущих генераций.
- R4 (brief «Критерии успеха» 3): рестарт bot, worker или postgres во время обработки не теряет принятый запрос — после старта он доходит до изображения или текста ошибки.
- R5 (brief «Зачем этот проект»; addendum «Провайдер моделей»): одно сообщение пользователя даёт не больше одной платной генерации, в том числе при повторной доставке обновления Telegram и повторе шага; окно сбоя между приёмом запроса Polza и сохранением её id принято (spine AD-4).
- R6 (brief «Критерии успеха» 3; addendum 429): временные ошибки Polza (таймаут, 429, 5xx, недоступность) повторяются без участия пользователя с конечным бюджетом; по его исчерпании пользователь получает «сервис временно недоступен».
- R7 (brief «Критерии успеха» 3; addendum 402/403; spine AD-6, AD-7): каждый принятый запрос не позже 30 минут после приёма завершается изображением или понятным текстом: модерация — «запрос отклонён модерацией, переформулируйте», некорректный запрос — «попробуйте изменить текст», остальное — «сервис временно недоступен»; сырой текст ошибки провайдера пользователю не показывается.
- R8 (spine «Consistency Conventions», Сообщения бота): `/start` отвечает приветствием с инструкцией; на не-текстовое сообщение бот подсказывает прислать текстовое описание, генерация не запускается.
- R9 (brief «Критерии успеха» 2, «Границы» Входит): все сервисы развёрнуты на VPS и работают; после перезагрузки сервера или падения процесса поднимаются сами, без ручных действий.
- R10 (spine «Consistency Conventions» Логи, «Deferred» оповещение): автор по JSON-логам восстанавливает путь любой генерации по `generationId` — шаги, попытки, причину отказа и `trace_id` Polza; 402 и ошибки конфигурации пишутся уровнем `error`.
- R11 (spine «Structural Seed», окружения local и prod; Decision 2026-11-16): весь стек — migrate, postgres, bot, worker — поднимается локально одной командой `docker compose`; упавший процесс поднимается сам.

## Constraints

- Стек зафиксирован: Node.js 26, TypeScript 6 (ESM), NestJS 12 монорепо, grammY, PostgreSQL 18, pg-boss, Drizzle, pino; цель — стек, новый для автора (brief «Риски»; spine «Stack»).
- Единственный провайдер — Polza.ai Media API: асинхронный `POST /v1/media` и опрос `GET /v1/media/:id`, без callback; ключа идемпотентности нет, повтор submit — новая платная генерация; запрос с ошибкой не оплачивается, а обрыв по таймауту на нашей стороне оплачивается (addendum «Провайдер моделей»; spine AD-4, AD-5).
- PostgreSQL — единственный источник истины, очередь pg-boss в той же базе; Redis и брокеры не используются (spine AD-1).
- Docker Compose — один файл для local и prod; до эпика деплоя целевая среда — локальная машина, затем один VPS вне РФ (Decision 2026-11-16; spine «Structural Seed»).
- Telegram-клиент принимает адрес прокси из env и без него ходит напрямую; адрес прокси — секрет, не логируется (Decision 2026-11-16; research «Risks»).
- Telegram только через long polling в одном экземпляре bot, без webhook и публичного HTTPS (brief «Риски»; spine AD-8).
- Модель фиксирована на сервере (`POLZA_MODEL`), пользователь её не выбирает (brief «Границы» Не входит; spine AD-10).
- Шаблоны следующей версии добавляются без переделки: текст пользователя, промт и параметры модели хранятся раздельно, обогащение промта — отдельный шаг перед submit (brief «Что дальше»; spine AD-10).
- Лимиты Telegram: фото до 10 MB, файл до 50 MB, около 1 сообщения в секунду на чат (research «Telegram platform rules»; addendum).
- Секреты (`TELEGRAM_BOT_TOKEN`, `POLZA_API_KEY`, `DATABASE_URL`) только в `.env` на машине запуска (локально, затем на VPS) — не в репозитории и не в логах; с невалидным конфигом процесс не стартует (spine «Consistency Conventions»).

## Done when

- Пользователь из белого списка в проде отправляет текст и получает изображение; пользователь вне списка — отказ.
- bot, worker и postgres подняты на VPS через `docker compose` и переживают перезагрузку сервера.
- Весь стек поднимается локально одной командой `docker compose`.
- Демонстрация на локальном compose или проде: рестарт worker, bot и postgres посреди генерации не теряет запрос; искусственные 429/503 от Polza повторяются; 402 и 403 дают пользователю понятный текст.
- Историю любой генерации можно восстановить по логам по её `generationId`.
- Портфолио-документ описывает систему такой, какой она реализована.

## Boundaries

- Не входит: шаблоны генерации и обогащение промта (следующая версия), загрузка своего фото и редактирование, выбор модели пользователем, монетизация и платежи (Stars), публичный доступ (brief «Границы» Не входит).
- Не входит: метрики, дашборды и трейсинг, оповещение автора о балансе, дневной лимит на пользователя, сверка двойных списаний, CI/CD и бэкапы БД, собственное хранилище изображений (spine «Deferred»).
- Touch point: Telegram Bot API — получение обновлений, отправка сообщений, фото и файлов; внешний; owner: epic-text-to-image.
- Touch point: Polza.ai API и CDN — создание генерации, опрос статуса, скачивание результата; внешний, баланс пополняет автор; owner: epic-text-to-image (клиент), epic-fault-tolerance (классификатор ошибок).
- Touch point: прокси для Telegram — xray (VLESS) на хосте автора, вне стека, настраивает автор; адрес его входа задаётся в env; owner: epic-text-to-image.
- Touch point: VPS-провайдер — аренда и настройка одного сервера вне РФ; owner: epic-vps-deploy.
- Сквозной путь: текст в Telegram → bot проверяет белый список и принимает запрос → worker отправляет в Polza и опрашивает статус → worker доставляет изображение или текст ошибки в чат.
